# Migration guide for v23

## API keys no longer survive native PHP serialization

This affects integrations that persist SDK resources or collections in PHP sessions, caches, or queued jobs and rely on their API keys being restored by `unserialize()`.

Native `serialize()` now omits the API key in `Stripe\Util\RequestOptions`, including request options attached to resources, nested objects, and collections. Deserialization restores that key as `null`, even when reading serialized objects written by older SDK versions. You can still read restored resource data; instance API operations such as `refresh()`, `save()`, and pagination need authentication supplied again.

### Authenticate restored objects explicitly

Before, code could rely on an embedded API key:

```php
$customer = unserialize($trustedStoredCustomer);
$customer->refresh();
```

After, obtain the appropriate key from secure runtime configuration and set it before making instance requests:

```php
$customer = unserialize($trustedStoredCustomer);
$customer->setApiKey($apiKeyFromSecureConfiguration);
$customer->refresh();
```

`setApiKey()` accepts a non-empty string and returns `void`. It always updates the receiving object and all reachable nested `StripeObject` values, including resources inside arrays and collections. Shared and cyclic resource references are supported. It does not make an API request, change resource values or pending updates, or modify global configuration or unrelated objects.

Each resource retains its existing noncredential options, including custom headers, connected-account and context settings, API version, API base, and retries. Recursion intentionally overwrites differing nested credentials: the supplied key must be authorized for every retained account context. Do not pass a mixed-credential graph to this helper unless a single key is appropriate for the entire graph. Serializing again omits the newly supplied key too.

### Global fallback and explicit keys

There is no automatic reconnection to the original `StripeClient`. Without an explicit resource key, PHP can use a key configured with `\Stripe\Stripe::setApiKey(...)` through existing request-time fallback. A restored object is therefore not necessarily unauthenticated. If neither a resource key nor a global key is available, its instance requests fail authentication.

Calling the resource's `setApiKey()` explicitly binds the supplied key to the resource graph, independently of the global key, without changing global configuration. Existing explicit per-call keys still take precedence over resource keys. Prefer explicit resource authentication in applications that use multiple keys.

### Collections and subsequent responses

Setting a collection's key also updates resources already contained in it. Pagination requests use that key, and new pages and their resources receive it through the existing response-option propagation:

```php
$customers = unserialize($trustedStoredCustomers);
$customers->setApiKey($apiKeyFromSecureConfiguration);
$customers->data[0]->refresh();
$nextPage = $customers->nextPage();
```

Likewise, nested objects created by a subsequent `refresh()` receive the effective request key. No client or requestor construction is needed.

### Prefer storing IDs or selected data

Instead of persisting SDK objects, store resource IDs and retrieve resources through a configured client when needed:

```php
$stripe = new \Stripe\StripeClient($apiKeyFromSecureConfiguration);
$customer = $stripe->customers->retrieve($storedCustomerId, [], [
    'stripe_account' => $connectedAccountIdFromConfiguration,
]);
```

Only use `unserialize()` with trusted data. Never persist an API key alongside a serialized object. These hooks do not sanitize arbitrary response data, custom headers, or directly serialized clients or requestors. The credential exposure of `var_export()` output remains a separate security consideration; these hooks do not make it safe. Persisting selected data also requires appropriate protection for that data.

Upgrading does not remove API keys from existing sessions, caches, queues, or backups. Review those stores separately and rotate any credentials that may have been exposed.
