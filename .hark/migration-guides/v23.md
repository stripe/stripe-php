# Migration guide for v23

## API keys no longer survive native PHP serialization

This affects integrations that persist SDK resources or collections in PHP sessions, caches, or queued jobs and rely on their API keys being restored by `unserialize()`.

Native `serialize()` now omits the API key in `Stripe\Util\RequestOptions`, including request options attached to resources, nested objects, and collections. Deserialization restores that key as `null`, even when reading serialized objects written by older SDK versions. You can still read restored resource data; instance API operations such as `refresh()`, `save()`, `delete()`, and auto-pagination need authentication supplied again.

### Pass an API key to instance methods on restored objects

Before, code could rely on an embedded API key:

```php
$customer = unserialize($trustedStoredCustomer);
$customer->refresh();
```

After, obtain the appropriate key from secure runtime configuration and pass it in the method's options:

```php
$customer = unserialize($trustedStoredCustomer);
$customer->refresh(['api_key' => $apiKeyFromSecureConfiguration]);
$customer->save(['api_key' => $apiKeyFromSecureConfiguration]);

$customers = unserialize($trustedStoredCustomerList);
foreach ($customers->autoPagingIterator(['api_key' => $apiKeyFromSecureConfiguration]) as $customer) {
    // ...
}
```

`refresh()` and `autoPagingIterator()` on `Stripe\Collection`, `Stripe\SearchResult`, `Stripe\V2\Collection`, and `Stripe\V2\SearchResult` now accept an optional `$opts` argument for this. Other instance methods, such as `save()`, `delete()`, and resource actions like `cancel()`, already accept request options.

Each restored resource keeps its other request options, including connected-account and context settings, API version, API base, and retries. If you set a global API key with `Stripe::setApiKey()`, restored objects continue to use it when no per-call key is passed.
